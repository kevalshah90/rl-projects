    The train baseline: measuring the untrained policy

    Before any RL, the same episode runs over a sample of train tasks with the untrained Qwen3.5-9B. Nothing is learned; the rewards give each task a pass rate p = passes / 4. Only tasks with 0 < p < 1 give GRPO mixed groups to learn from, so they go into splits/trainable.txt.

    Run with vf-eval @ configs/baseline_train.toml -n 30, summarized by s09_baseline.py. Train only: dev stays held out for evaluation.

    Async training: rollouts and training overlap

    In synchronous training, rollouts stop while the trainer steps. In async training (prime-rl), the policy server keeps sampling rollouts with the weights it has while the trainer computes the next ones. A batch can therefore be a few versions behind the trainer: it is off-policy. prime-rl drops rollouts older than max_off_policy_steps = 4, and the importance ratio in the loss corrects for the gap that remains.

    C1, our own loop (step 11)

    Synchronous, one H100: vLLM samples a batch, then sleeps and frees its memory, the trainer steps, the new weights are copied into vLLM, and it wakes. Every rollout is on-policy. Single-turn: one answer per task, no check tool.

    C2, prime-rl (steps 12–13)

    Async on two H100s, inference on one and the trainer on the other, with the orchestrator in the same Modal container. Multi-turn with the check tool, exactly the episode shown above. The interception server moves into Modal with the orchestrator; sandboxes still reach it through a tunnel.
